# M4.2–M4.6: technische Arbeitsgrundlage (Zusammenfassung)
Quelle: Notion M4.2 – Technische Spezifikation v1.0 und spätere M4.4-Entscheidungen. Die vollständige Original-Spezifikation liegt in Notion, ältere Implementierungsdokumente in den Original-ZIPs.

Module: domain/game (Zustandsmaschine, Blinds), domain/quiz (Auswahl und Projektion), content (JSON-Import/Schema), persistence (IndexedDB), analytics (Event-Outbox/API), UI (State-Views), dashboard (geschützt), tests. Kein Notion-Live-Zugriff als Laufzeitabhängigkeit. Ursprünglich React/Vite empfohlen, tatsächlich browsernatives JavaScript und TypeScript Core umgesetzt. PostgreSQL/Node-API nur Vorschlag für später.

Game setup → active ↔ paused → finished/abandoned. Phase question → hint1 → hint2 → answer → settled. advancePhase jeweils ein Schritt; keine Rücksprünge nach Reveal. startGame validiert Setup. finishHand zählt einmal, neue Frage/Blinds; v0.2.2 manuelles Partieende statt Eliminationsdialog. earlyFinish, allInRunout, reportQuestion, skipQuestion, pause/resume, abandon. Physische Potlogik bleibt am Tisch.

Quiz Engine: Schema 1.4, aktive Fragefelder getrennt von Archivtexten; source_checked nur Test, Release nur approved/releaseReady. Nie gezeigte Fragen zuerst zufällig, dann least-recently-shown unter noch nicht in dieser Partie verwendeten IDs, Wiederverwendung erst bei erschöpftem Pool nach Warnung/Bestätigung. Gemeldete/übersprungene IDs für Partie sperren. Revision und Datasetversion zusätzlich speichern; aktive Hand snapshotten; keine Doppelzählung bei Reload.

Persistenz-Soll: IndexedDB gameSessions, questionHistory, seen/blocked IDs, eventOutbox; atomare gültige Aktionen mit stateVersion/commandId, Wiederherstellung, keine stillen Löschungen, Versionsmigration, sichtbare Storagefehler, Mehrtab-Schutz, aktive Zeit best effort. Offline nach erfolgreichem Caching; kein Versprechen beim ersten Offline-Besuch. Aktuelle Standalone ist nicht mit dem vollständigen Core/Web-Paket gleichzusetzen.

Analytics-Soll: lokale Fragenhistorie getrennt von zentraler Statistik, pseudonyme Session-ID; game_started, question_shown, phase_revealed, context_opened, explanation_opened, hand_completed, question_reported/skipped, players_eliminated (nur wo erfasst), game_paused/resumed/finished/abandoned. eventId, sessionId, handId, questionId/Revision, datasetVersion, preset, initial/activePlayers (wo verfügbar), phase, elapsedMs, timestamp, eventSchemaVersion. Keine Namen, Antworten, Chipstände oder dauerhaften Geräte-IDs. Telemetrie erst mit transparenter Info/geeigneter Rechtsgrundlage, lokale Partie ohne Telemetrie möglich. API POST /api/events, Batch/Schema/Rate-Limit, idempotente eventId UNIQUE, Outbox Retry/Backoff; Dashboard geschützt; Aufbewahrung/Löschung offen. Keine physischen Schätzfehler/Potgrößen/Fold-Raten messbar. KPIs: Starts/Enden/Abbrüche, Abschlussquote, Dauer, Hände, Preset, Spielerzahl, Fragenanzeigen/Abschlüsse, Poolabdeckung, Kategorienmix, Skip-/Meldequote, optionale Kontext-/Erklärungsöffnungen.
